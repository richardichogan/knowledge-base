# Knowledge Hub — Custom Canvas Spec
## v1 — No third-party canvas libraries

---

## What this is

A custom-built infinite canvas embedded in the Knowledge Hub web app,
rendered via the browser Canvas API (HTML `<canvas>`). No tldraw, Excalidraw,
React Flow, or any third-party diagramming library.

The canvas is a spatial thinking and synthesis workspace. It is not a diagram
tool, not a whiteboard, and not a flowchart builder. Its purpose is to let
Richard spatially arrange knowledge items from the hub — notes, sparks, discover
articles, AI outputs, concepts — and draw connections between them to surface
structure that isn't visible in a linear list or timeline.

---

## Why custom

The previous attempt used tldraw. It was removed because:

- Too heavy — massive bundle, not designed for this use case
- Wrong primitive model — shapes and stickers, not knowledge items
- Opaque data model — hard to persist meaningfully to PostgreSQL
- No integration path — items from Discover/Think/Library couldn't be
  first-class nodes without hacking the library internals

A custom canvas renderer gives full control over node types, data model,
persistence, and rendering performance.

---

## Core mental model

A **canvas** is a named, persistent spatial document stored in PostgreSQL.
It contains:

- **Nodes** — positioned items on the canvas surface
- **Edges** — typed directed connections between nodes
- **Viewport state** — pan/zoom position, persisted per-canvas

Nodes are either:
1. **Hub references** — a pointer to an existing knowledge hub item
   (discover article, spark, note, AI session, task, content item)
2. **Freeform text blocks** — standalone text written directly on the canvas
3. **AI output blocks** — text generated by the AI placed as a node

Edges are typed: `relates-to`, `supports`, `contradicts`, `leads-to`, `part-of`.

## Data model

### `canvases` table

```sql
CREATE TABLE canvases (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title       TEXT NOT NULL,
  description TEXT,
  project     TEXT,          -- 'personal' | 'structara' | 'ibm'
  viewport    JSONB NOT NULL DEFAULT '{"x":0,"y":0,"zoom":1}',
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### `canvas_nodes` table

```sql
CREATE TABLE canvas_nodes (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  canvas_id   UUID NOT NULL REFERENCES canvases(id) ON DELETE CASCADE,
  node_type   TEXT NOT NULL,     -- 'hub_ref' | 'text' | 'ai_output'
  ref_type    TEXT,              -- 'discover_item' | 'spark' | 'note' | 'content_item' | 'ai_session'
  ref_id      TEXT,              -- id of the referenced hub item
  label       TEXT,              -- display label (overrides ref item title if set)
  body        TEXT,              -- for text and ai_output nodes
  x           NUMERIC NOT NULL DEFAULT 0,
  y           NUMERIC NOT NULL DEFAULT 0,
  width       NUMERIC NOT NULL DEFAULT 280,
  height      NUMERIC NOT NULL DEFAULT 80,  -- auto-sizes for content, this is min
  colour      TEXT,              -- optional accent colour
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### `canvas_edges` table

```sql
CREATE TABLE canvas_edges (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  canvas_id   UUID NOT NULL REFERENCES canvases(id) ON DELETE CASCADE,
  source_id   UUID NOT NULL REFERENCES canvas_nodes(id) ON DELETE CASCADE,
  target_id   UUID NOT NULL REFERENCES canvas_nodes(id) ON DELETE CASCADE,
  edge_type   TEXT NOT NULL DEFAULT 'relates-to',
  label       TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## Renderer architecture

All rendering is done via `CanvasRenderer` — a class that manages a single
`<canvas>` element. React owns the mount/unmount lifecycle; all draw calls
happen imperatively inside the renderer.

### Coordinate systems

- **World space** — the infinite canvas coordinate system (origin `0,0`)
- **Screen space** — pixel coordinates on the `<canvas>` DOM element

Transform: `screen = world * zoom + pan`
Inverse: `world = (screen - pan) / zoom`

The renderer maintains `{ panX, panY, zoom }` as its primary view state.

### Render loop

Uses `requestAnimationFrame` only when dirty (not a continuous loop).
A `dirty` flag is set on any interaction (pan, zoom, drag, selection change).
The renderer calls `ctx.clearRect` and redraws all visible nodes and edges
each frame. Offscreen culling skips nodes outside the current viewport.

### Node rendering

Each node is a rounded rectangle drawn with `ctx.roundRect` (or polyfilled).
Content inside nodes:
- Hub ref nodes: source chip (small), title text (wrapping, bold), metadata line
- Text nodes: body text, wrapping, editable inline
- AI output nodes: italic body, slightly different background

Text wrapping is handled manually — `ctx.measureText` used to break lines
at the node width boundary. Line height `1.5 * fontSize`.

Selected nodes get a 2px teal (`var(--kh-accent)`) stroke.

### Edge rendering

Edges are drawn as cubic bezier curves between node connection points
(nearest edge midpoint, not fixed anchor). Arrow head at target end
drawn with `ctx.lineTo` geometry. Edge labels are drawn centered on the
curve midpoint if present.

Hover detection on edges uses point-to-bezier distance approximation
(sample 30 points along curve, check distance < 6px).

## Interaction model

### Viewport navigation

| Gesture | Action |
|---|---|
| Click + drag on empty space | Pan |
| Scroll wheel / trackpad pinch | Zoom (centred on cursor position) |
| Cmd + 0 | Reset zoom to 1.0 |
| Cmd + Shift + H | Fit all nodes in viewport |

Zoom range: 0.1× to 3.0×. Zoom is smooth — delta applied per scroll event,
not stepped.

### Node interactions

| Gesture | Action |
|---|---|
| Click node | Select (deselects others) |
| Shift + click node | Add to / remove from selection |
| Click + drag node | Move (updates x/y on pointer up, persists to server) |
| Double-click text/ai node | Enter inline edit mode |
| Right-click node | Context menu (Edit label, Change colour, Delete, Open original) |
| Click empty space | Deselect all |

Multi-select drag moves all selected nodes together (maintain relative offsets).

### Edge creation

- Hover a node → connection handle dots appear at edge midpoints (N/S/E/W)
- Click + drag from a handle → draws a temporary edge line
- Drop onto another node → creates the edge (prompt for edge type via small popover)
- Drop onto empty space → cancel

### Adding nodes

Three entry points:

1. **Command palette** (`Cmd+K` while canvas is focused) — search hub items,
   select one, it appears at canvas centre
2. **Drag from sidebar panel** — a collapsible right-hand panel lists recent
   hub items (Sparks, Discover, Notes); drag one onto the canvas
3. **Double-click empty space** — creates a new freeform text node at that
   position and enters edit mode immediately

## Component structure

```
src/
  features/
    canvas/
      CanvasPage.tsx          — route wrapper, loads canvas list or redirects to editor
      CanvasList.tsx          — list of saved canvases with create/delete
      CanvasEditor.tsx        — full-page editor: toolbar + renderer + sidebar
      CanvasRenderer.ts       — imperative class, owns <canvas> element
      CanvasToolbar.tsx       — zoom controls, fit, add-text button, edge type selector
      CanvasSidebar.tsx       — searchable hub item list, draggable into canvas
      useCanvasState.ts       — React state: nodes, edges, viewport, selection
      useCanvasPersist.ts     — debounced save (positions, viewport) to API
      canvasGeometry.ts       — pure utils: hit test, bezier point, world↔screen
      canvasTypes.ts          — CanvasNode, CanvasEdge, Viewport, EdgeType types
```

No file over 200 lines (per code standards). `CanvasRenderer.ts` is the
one exception — likely 300–400 lines — document why in file header.

## API routes

All under `/api/canvas`:

```
GET    /api/canvas                       list all canvases
POST   /api/canvas                       create canvas
GET    /api/canvas/:id                   get full canvas (nodes + edges)
PATCH  /api/canvas/:id                   update title/description/viewport
DELETE /api/canvas/:id                   delete canvas

POST   /api/canvas/:id/nodes             add node
PATCH  /api/canvas/:id/nodes/:nodeId     update node (position, label, body)
DELETE /api/canvas/:id/nodes/:nodeId     delete node

POST   /api/canvas/:id/edges             add edge
DELETE /api/canvas/:id/edges/:edgeId     delete edge
```

Viewport is persisted on the canvas record (PATCH `/api/canvas/:id`)
with a 1-second debounce after pan/zoom stops.

Node positions are persisted on pointer-up after a drag, not continuously.

---

## Persistence strategy

- Full canvas (nodes + edges) loaded once on open — no live subscription needed
- Node moves: debounced PATCH 300ms after drag ends per node (or bulk PATCH
  for multi-select moves)
- New nodes/edges: immediate POST
- Deletes: immediate DELETE
- Viewport: debounced PATCH 1s after pan/zoom settles
- No optimistic update complexity — canvas is a single-user local tool;
  conflicts won't occur

## AI integration

From within the canvas editor, the user can:

1. **Ask AI about the canvas** — sends all node titles/bodies + edge types
   as context; AI responds in a small floating panel; response can be
   added to canvas as an AI output node
2. **Ask AI to suggest connections** — AI reviews node titles and suggests
   edges; user accepts or dismisses each suggestion
3. **Summarise canvas** — AI produces a prose summary of the canvas structure;
   output can be saved as a spark or note

These actions go via the existing `/api/ai/chat` endpoint with a
`canvas_context` system message block prepended by `contextBuilder.ts`.

## Navigation integration

Canvas lives under the **Think** tab alongside Notes and Sparks.

```
/think             → Think page (Notes | Sparks | Canvas tabs)
/think/canvas      → CanvasList
/think/canvas/:id  → CanvasEditor
```

The Think tab in the topnav gains a dot indicator if there are unsaved
canvases (likely not needed — persistence is automatic, so this is low priority).

## Layout

`CanvasEditor` is a full-height page (`height: 100%`, no page-root padding).
Layout:
```
┌─ CanvasToolbar (3rem, flex-shrink: 0) ─────────────────────────────┐
│  zoom –/+  |  fit all  |  add text  |  edge type selector  |  title │
├─ canvas body (flex: 1, overflow: hidden) ───────────────────────────┤
│  <canvas> element fills 100% width/height                            │
│  CanvasSidebar (absolute right, collapsible, 260px wide)            │
│  AI panel (absolute bottom-right, slide-up, 360px wide)             │
└─────────────────────────────────────────────────────────────────────┘
```

The `<canvas>` element is resized via `ResizeObserver` — `canvas.width`
and `canvas.height` set to `devicePixelRatio * clientWidth/Height` for
sharp rendering on retina screens.

## Styling

All canvas chrome (toolbar, sidebar, panels) uses the same dark g100 Carbon
token variables as the rest of the app. The `<canvas>` element background
is `var(--cds-background)` set via `ctx.fillRect`.

Grid/dot pattern on canvas background: small dots at 24px world-space
intervals, drawn as 1px circles, colour `var(--cds-border-subtle-00)` at
low opacity, scale with zoom.

## Performance targets

- 200 nodes, 300 edges: 60fps pan/zoom with no jank
- Node drag: pointer lag < 1 frame
- Offscreen culling applied at > 100 nodes
- Initial load of a 200-node canvas: < 400ms (single SQL join query)

---

## What canvas is NOT

- Not a flowchart or diagram tool — no shape library
- Not a presentation tool — no slide metaphor
- Not real-time collaborative — single-user only
- Not a whiteboard — no freehand drawing
- Not a mind map tool — connections are optional, not required
- Not a replacement for notes — text nodes are brief labels, not documents

---

## Out of scope for v1

- Image nodes (drag an image onto canvas)
- Nested canvases (node that links to another canvas)
- Export to PNG/SVG
- Keyboard-only node creation (beyond Cmd+K)
- Undo/redo (complex — defer to v2; warn user before delete)
- Canvas templates
- Node grouping / frames

## Open questions

1. **Sidebar vs Command Palette for node addition** — sidebar panel adds weight
   to the editor layout; Cmd+K alone may be sufficient. Decide on first
   implementation.

2. **Edge type on creation** — should edge type default to `relates-to` silently
   (faster) or always prompt (more intentional)? Lean toward silent default
   with ability to change on right-click.

3. **Canvas list placement** — own page under `/think/canvas` or a modal
   triggered from the Think tab toolbar? Modal is lighter.

4. **Hub ref node depth** — show just title + source, or also show synopsis?
   Synopsis makes nodes taller but more useful when offline from the original
   item. Decision: title + source only; synopsis on hover tooltip.
